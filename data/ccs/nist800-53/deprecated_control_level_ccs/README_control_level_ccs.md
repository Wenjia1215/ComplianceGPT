README: NIST SP 800-53 Canonical Clause Store (CCS)
===================================================

This directory contains the processed, version-aware data files for **NIST Special Publication 800-53 (Revisions 4 and 5)**, formatted for use in the ComplianceGPT RAG system.

Overview
--------

The files in this collection represent the "Canonical Clause Store" (CCS) for NIST SP 800-53. The data is derived from the official NIST OSCAL (JSON) releases and has been processed into a JSONL format, where each line represents a single, addressable control or control enhancement. This granular, versioned structure is the foundation for the project's retrieval, answering, and delta-tracking components.

File Descriptions
-----------------

### 1\. Core Control Catalogs (The Corpus)

These files are the primary source of truth for the control text. They are indexed by the retriever (e.g., BM25) to find relevant clauses.

*   NIST\_SP-800-53\_rev4\_catalog.jsonl
    
    *   **Description**: The complete, processed catalog for NIST SP 800-53 **Revision 4**. Each line is a single control (e.g., "AC-1") or enhancement (e.g., "AC-2 (1)") in JSON format.
        
*   NIST\_SP-800-53\_rev5\_catalog.jsonl
    
    *   **Description**: The complete, processed catalog for NIST SP 800-53 **Revision 5**.
        

### 2\. ODP Registries (Parameter Detection)

These files are lookup tables generated by parsing the core catalogs. They identify all Organization-Defined Parameters (ODPs) and provide metadata for them.

*   odp\_registry\_rev4.jsonl
    
    *   **Description**: A JSONL registry of every ODP (e.g., {{ insert: param, ac-2\_prm\_3 }}) found in the Rev. 4 catalog. This allows the system to quickly identify which controls require organizational input.
        
*   odp\_registry\_rev5.jsonl
    
    *   **Description**: The corresponding ODP registry for the Rev. 5 catalog.
        

### 3\. Organizational Profiles (Parameter Filling)

These YAML files store the _organization's specific values_ for the ODPs. This is how the system implements the FILL\_FROM\_PROFILE logic.

*   org\_profile\_blank\_rev4.yaml & org\_profile\_blank\_rev5.yaml
    
    *   **Description**: Blank templates containing all possible ODP keys for each revision. An organization would fill these out to create their compliance profile.
        
*   org\_profile\_example\_rev4.yaml & org\_profile\_example\_rev5.yaml
    
    *   **Description**: Sparsely populated example profiles used for testing and demonstrating the FILL\_FROM\_PROFILE functionality.
        

### 4\. Version Delta File (Change Tracking)

This file maps the changes between the two revisions, enabling the "delta-aware" features of the project.

*   rev4\_to\_rev5.delta.jsonl
    
    *   **Description**: A JSONL file where each line represents a change for a specific control ID from Rev. 4 to Rev. 5. This file is crucial for auditing version-to-version changes.
        

Key Concepts
------------

### Delta Logic

The change field in rev4\_to\_rev5.delta.jsonl is defined as follows:

*   **REMOVED**: Marked only when a Rev. 4 control ID is completely absent from Rev. 5. (Note: For NIST SP 800-53, most controls were modified, not removed, so this status is rare).
    
*   **MODIFIED**: Marked for any control that exists in both revisions but has changes to its text, parameters, or other properties.
    
*   **ADDED**: Marked for any brand-new control ID that appears in Rev. 5 but did not exist in Rev. 4.
    

### Data Provenance

The raw data for these catalogs was sourced from the official NIST OSCAL content repository:

*   **Source**: [[(https://github.com/usnistgov/oscal-content/tree/main/nist.gov/SP800-53)](https://github.com/usnistgov/oscal-content/tree/main/nist.gov/SP800-53)]
    
*   **Processing**: The original monolithic OSCAL JSON files were parsed and flattened into the line-oriented JSONL format to create a clean, searchable corpus for retrieval.
